# Bobine 5.0.6 — synthèse de revue de l’outillage et de la livraison

Date : 28 octobre 2026. Document de revue du candidat, pas attestation de publication Stable.

## 1. Objet et conclusion de revue

Le changement prépare le cycle 5.0.6 en fiabilisant les constructions et les préversions. Il traite la panne d’acquisition du NDK Android, l’ordre incorrect des préversions Linux et plusieurs contrôles insuffisants de signature, d’architecture et d’arrêt des tâches.

Le socle `170253dcd23d38478e5686ef02bf913a1982ea14` a passé une CI complète : **28 jobs réussis et 6 jobs de publication ignorés**. Le workflow Play a également construit ses artefacts avec succès sans les publier. Des compléments de revue renforcent ensuite les contrôles AAB et les courses d’arrêt asyncio ; leur qualification finale doit être lue dans le relevé de validation ci-dessous.

La compatibilité de construction est établie sur les runners concernés. L’acceptation sécurité et la recette physique restent distinctes. Les avis affectant certaines dépendances Android et GTK empêchent de déduire un feu vert Stable des seuls builds verts.

## 2. Changements, raisons et mécanismes

### Acquisition Android et source des versions

**Problème.** La CI échouait pendant l’installation du NDK `28.2.13676358` : archive ZIP illisible. L’échec précédait la compilation applicative et faisait échouer `ci-ok` en cascade. La procédure était dupliquée entre CI et Play.

**Implémentation.** `android/toolchain.json` décrit API 36, minSdk 34, build tools 36.1.0 et NDK r28c. `scripts/ci/setup-android-sdk.py` installe les petits paquets via sdkmanager et gère séparément le NDK : contrôle de taille et SHA-1 du dépôt officiel Google, contrôle CRC du ZIP, extraction dans un répertoire temporaire, contrôle de révision et démarrage des outils LLVM avant publication de l’installation. Une installation existante n’est réutilisée qu’après contrôle ; une installation partielle est conservée sous un autre nom pour diagnostic. Les reprises sont bornées et les erreurs permanentes HTTP, droits ou espace disque restent bloquantes.

**Choix.** Le couple AGP 9.2.1/Chaquopy 17.0.0 reste dans sa plage de compatibilité documentée. Le wrapper Gradle 9.7.1 reçoit son SHA-256 officiel. Aucun passage opportuniste à Gradle 10 n’est introduit. Le helper vise les hôtes Linux des workflows Android ; ce n’est pas un installateur SDK universel Windows/macOS.

**À relire.** Gestion des erreurs transitoires, conservation des modes exécutables et liens symboliques du ZIP, refus des traversées de chemins et publication de l’arbre seulement après validation.

### Dépendances et compilateurs

**Problème.** Des résolutions et outils pouvaient évoluer entre deux builds d’une même version produit.

**Implémentation.** Les dépendances desktop/headless sont bornées dans `backend/constraints-desktop.txt`, séparément des outils de test et de packaging. Rust est épinglé par `rust-toolchain.toml` et les commandes Cargo utilisent les lockfiles. Les actions CI/Play sont référencées par commit avec leur version lisible. Les archives FFmpeg Windows ont un identifiant de release et des SHA-256 fixes ; le script vérifie aussi la signature PE, l’architecture x64/ARM64 et le démarrage réel de ffmpeg/ffprobe.

**Choix.** Le profil Chaquopy reste en Python 3.13 pour mobile et 3.11 pour TV ARM32/64, avec Pydantic v1. Les contraintes desktop Pydantic v2 ne sont pas injectées dans ce profil. Les contraintes ne constituent pas un verrouillage par hash de toutes les distributions et les paquets système des runners ne sont pas figés : aucune reproductibilité bit à bit des installateurs n’est revendiquée.

**À relire.** Plateformes et marqueurs des contraintes Python, absence de repli FFmpeg ARM64 vers x64, portée réelle des profils Android simulés sur hôte et des rapports `pip inspect`.

### Ordre Canary → Bêta → Stable

**Problème.** Le suffixe Debian `+canary.N` trie après la version Stable de même base. Les anciens formats RPM et Arch ne garantissaient pas non plus toute la promotion attendue.

**Implémentation.** Le registre `backend/app/release_channel.py` dérive les trois formats, consommés par les adaptateurs de packaging. Pour une même base :

| Canal | Debian | RPM Version-Release | Arch pkgver-pkgrel |
|---|---|---|---|
| Canary 42 | `5.0.6~0.canary.42` | `5.0.6-0.1.canary.42` | `5.0.6alpha.42-1` |
| Bêta 7 | `5.0.6~1.beta.7` | `5.0.6-0.2.beta.7` | `5.0.6beta.7-1` |
| Stable | `5.0.6` | `5.0.6-1` | `5.0.6-1` |

**Choix.** Les anciennes formes restent lisibles. La montée de base 5.0.5 → 5.0.6 est nécessaire : remplacer le suffixe de la seule base 5.0.5 rétrograderait une ancienne Canary Debian. Les noms d’assets rolling et les tags mobiles restent fixes, `beta` et `canary`.

**À relire.** Comparaison numérique de builds 9 → 10, priorité entre canaux indépendamment du numéro de build, migration depuis les formes déjà distribuées, cohérence des icônes et des canaux avec le registre.

### Intentions de publication, signatures et Google Play

**Implémentation.** `resolve-release.py` refuse les intentions manuelles incompatibles et exige la cohérence du tag Stable avec VERSION. Les compléments imposent `Vx.y.z` pour les nouvelles Stables. `check-android-signing.py` traite les quatre secrets comme un ensemble : configuration partielle toujours refusée ; absence totale admise seulement pour les validations de PR sans signature. Les builds de bundles et les composants requis ARM64 deviennent bloquants.

La vérification AAB est commune à CI et Play : manifeste, ABI exactes, bibliothèques attendues, Python embarqué, absence de chemins ZIP dupliqués et vérification JAR stricte. Le code de sortie 4 est admis pour le certificat de téléversement autosigné ; les entrées non signées, les modifications d’entrées signées et les autres erreurs restent bloquantes. Ce contrôle ne remplace pas une politique de confiance d’un certificat tiers ; l’acceptation du code 4 ne constitue pas une validation PKI de sa chaîne ou de ses dates.

Le workflow Play utilise les helpers et le compilateur Rust de la révision du workflow, même si `source_ref` sélectionne un ancien code produit. L’envoi vers la boutique nécessite une entrée explicite `upload_to_play`; un compte de service absent fait échouer un envoi demandé. La construction seule ne publie donc aucun brouillon. Les APK Play passent signature, alignement 16 Kio, ABI et refus de `REQUEST_INSTALL_PACKAGES`.

**À relire.** Distinction entre signature cryptographique et confiance du certificat ; codes stricts JAR acceptés ; branches de configuration sans secret ; absence de publication implicite pendant une qualification.

### Backend : contrats et arrêt des tâches

**Problème.** Les routes GET/HEAD produisaient des IDs OpenAPI dupliqués. L’envoi WebSocket depuis un thread pouvait laisser une coroutine non attendue si la boucle s’arrêtait. Le chemin de nettoyage des périphériques pouvait aussi laisser des transports de sous-processus attachés à une boucle fermée.

**Implémentation.** Les six routes de médias conservent GET et HEAD, mais HEAD est exclu du schéma. Les événements WebSocket sont programmés par un callback thread-safe ; la coroutine n’est créée que si le callback s’exécute effectivement sur la boucle. L’arrêt après `is_running()` peut donc abandonner le callback sans laisser de coroutine allouée.

Les commandes système expirées ou annulées sont tuées, leurs pipes sont drainés et leur fin est attendue. Une annulation reste une annulation, et une expiration reste l’erreur métier `timeout`. Le service attend la fin du nettoyage des tâches annulées avant d’arrêter son pilote. Le warning SQLAlchemy lié au nettoyage des fixtures est corrigé par flush avant la suppression en masse ; aucun filtre global d’avertissements n’est ajouté.

**À relire.** Tests de course d’arrêt, ordre nettoyage/pilote, propagation de CancelledError, contrat HTTP HEAD et génération des IDs OpenAPI. La fermeture des tâches concerne tous les pilotes ; l’exécution des commandes modifiée est propre au pilote Linux.

### Prérequis web et version produit

La branche séparée `fix/lot1-release-probe` de BobineWeb contient uniquement la correction de sonde : comparer la Stable à VERSION de son propre tag, maintenir l’accord avec `latest.json`, autoriser main en avance et refuser une régression de main. Cette correction est isolée du travail parallèle du site.

La branche Bobine contient VERSION 5.0.6 et ses replis alignés (backend, install.sh, Inno Setup, Gradle, AppStream). Les liens publics Stable restent sur la dernière version publiée. La sonde web doit être fusionnée avant le passage de Bobine main à 5.0.6 et sa publication Canary automatique.

## 3. Preuves et portée de qualification

- [CI complète du socle 170253d](https://github.com/FantasmaGlad/Bobine/actions/runs/40557429855) : 28 jobs réussis ; les six jobs ignorés sont ceux de signature/publication des releases et dépôts, désactivés lors de ce déclenchement de validation.
- [Construction Play du même socle](https://github.com/FantasmaGlad/Bobine/actions/runs/40557277267) : deux AAB et deux APK Play, contrôles de contenu et de permissions ; aucune pièce jointe à une release ni envoi à la boutique.
- Backend du socle : 1 018 tests et 19 sous-tests sous chacun de Python 3.11/3.12/3.13, `pip check` réussi. Les compléments de revue ajoutent des régressions de cycle de vie et d’intégrité ; voir le relevé final ajouté en fin de document.
- Frontend : 359 tests, typage TypeScript et export statique ; parcours Firefox en CI. Aucun changement fonctionnel de l’interface dans ce lot.
- Gestionnaires Linux : sept transitions vérifiées par famille avec les vrais comparateurs dpkg, RPM/Fedora et vercmp/Arch. Les tests en conteneur ne modifient pas le paquet installé sur l’hôte.
- SDK/NDK : acquisition vierge réelle et réutilisation contrôlée ; scénarios d’archives tronquées, empreintes erronées, ZIP invalide, liens sortants, erreurs HTTP permanentes et disque plein.
- Signature AAB : véritables clés de fixture et jarsigner ; certificat autosigné admis, entrée ajoutée ou modifiée et doublon ZIP refusés. Ces clés temporaires ne signent aucun artefact distribué.
- Windows x64/ARM64 : runners natifs, contrôle du binaire FFmpeg, démarrage du backend empaqueté et production Inno Setup. Ceci ne certifie ni Authenticode ni une installation utilisateur sur matériel externe.
- Linux amd64/arm64 : paquets DEB, RPM et Arch construits et inspectés ; tests d’installation prévus par les workflows, avec limitations explicites des paquets d’une autre architecture.
- macOS : DMG construit, backend démarré, signature ad hoc ; pas de notarisation ni de recette Gatekeeper/Safari sur un Mac utilisateur.
- Android : APK mobile ARM64 et TV ARM32/64 signés ; alignement APK et composant Rust 16 Kio ; démarrage des variantes debug dans des émulateurs x86_64. Ces émulateurs ne valident pas les appareils ARM physiques.

## 4. Réserves avant promotion Stable

1. **Dépendances Android.** FastAPI 0.99.1/Pydantic 1.10.26 implique l’ancienne Starlette 0.27.0. Les métadonnées PyPI signalent plusieurs avis, notamment de consommation de ressources. FastAPI 0.125.0 est la dernière version qui accepte directement Pydantic v1, mais impose encore Starlette <0.51 ; une simple hausse de FastAPI ne résout donc pas tous les avis récents. La compatibilité Android TV 32 bits doit être traitée dans une qualification de runtime dédiée, avec évaluation des chemins exposés. Ne pas contourner les contraintes du résolveur pour faire disparaître un signalement.
2. **glib.** Les graphes Cargo de l’assistant et du projecteur contiennent glib 0.18.5 via GTK. Deux alertes GitHub modérées portent sur `VariantStrIter`. L’absence d’appel direct dans Bobine n’établit pas l’absence de chemin transitif. La correction amont est annoncée à partir de 0.20, changement qui ne se réduit pas à modifier le lockfile de GTK3.
3. **Recette réelle.** Pas de nouvelle validation Wyse, tablette/TV ARM, Windows ou macOS physique dans ce lot. Les sorties audio, autorisations OS, migrations utilisateur et cas PDF restent soumis aux lots fonctionnels et à leur recette.
4. **Publication.** Aucun tag V5.0.6, aucune Stable et aucune Bêta 5.0.6 ne sont déclarés publiés par ce document. L’envoi Play et la chaîne de signature des dépôts restent séparés des builds de validation.

Sources de ces réserves : [notes FastAPI 0.126.0](https://fastapi.tiangolo.com/release-notes/#01260), [métadonnées Starlette 0.27.0](https://pypi.org/pypi/starlette/0.27.0/json), [métadonnées Starlette 0.50.0](https://pypi.org/pypi/starlette/0.50.0/json), [avis glib](https://github.com/advisories/GHSA-wrw7-89jp-8q8g).

## 6. Reproduction des contrôles

Depuis la racine du dépôt, dans un environnement Python isolé conforme aux requirements :

```bash
python -m pytest backend/tests -q -W error::RuntimeWarning -W error::pytest.PytestUnraisableExceptionWarning
python3 -m unittest discover -s scripts/ci -p 'test_*.py' -q
python3 scripts/ci/test-package-versions.py --family debian
```

Les tests de signature exigent un JDK avec keytool/jarsigner. Les comparateurs RPM et Arch s’exécutent dans leurs conteneurs via le pipeline de paquets. La validation finale des compléments est celle de la CI attachée à leur commit : les anciens résultats du socle ne remplacent pas les nouveaux contrôles.
